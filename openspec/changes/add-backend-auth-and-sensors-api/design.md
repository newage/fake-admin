# Design

## Context

Репозиторій порожній (`backend/`, `frontend/`, `docker/`). Вимоги й відхилені альтернативи зібрані в `.agents/docs/first-decisions.md`; пагінація списку зафіксована в `docs/adr/0001-server-side-offset-pagination-for-sensors-list.md`. Frontend винесено в `add-admin-frontend`. Мотивація — у `proposal.md`, вимоги — у `specs/`. Консʼюмери, що пишуть показання, живуть поза цією зміною, тож таблиці `sensor_readings` немає.

## Goals / Non-Goals

**Goals:**
- Зріз від Docker до `GET /api/sensors`: міграції й сидер → OAuth → RBAC → API; стабільний контракт для `add-admin-frontend`.
- Стабільний контракт API, у якому режим калькулятора (`live`/`cached`) прихований від клієнта.

**Non-Goals:**
- Екрани керування користувачами, сесіями, матрицею прав; створення датчика; HMAC-перевірка, дедуплікація й консʼюмери; воркер кешу; конкретні калькулятори.
- Миттєве відкликання access-токена (свідомо: ≤5 хв).

## Decisions

**Топологія.** Один origin через nginx: `/` → статика SPA (лише заглушка до `add-admin-frontend`), `/api/*` і `/token` → PHP-FPM. Немає CORS. Логи nginx збирає fluent-bit; PHP пише через Monolog у stdout. Альтернатива (окремі origin) відкинута: CORS і складніший CSP без користі.

**Авторизація.** `league/oauth2-server` через `mezzio-authentication-oauth2`, password grant + refresh grant; access — JWT RS256, ключі з `.env`. Password grant обрано, бо клієнт один і власний; Authorization Code + PKCE відкладено до появи сторонніх клієнтів. `isAccessTokenRevoked` повертає `false` (реєстру access немає), відкликання — через `refresh_tokens` (хеш, `revoked_at`, ротація). Альтернативи: ручний JWT на `lcobucci/jwt`, `firebase/php-jwt` — відкинуті на користь готового стандарту.

**Перший вхід суперадміна.** Власний `UserEntityRepository` у потоці password grant: якщо `password_hash` порожній і email = `SUPERADMIN_EMAIL`, переданий пароль хешується й записується в одній транзакції з умовою `password_hash = ''`, щоб гонка двох входів не дала двох переможців. Ризик захоплення до першого входу прийнятий розробником.

**RBAC.** PSR-15 middleware після автентифікації бере роль із claims, ім'я маршруту з роутера й перевіряє `role_permissions(role_id, permission, constraints)`. `permission` — стабільний ключ маршруту (`sensors.list`, `sensors.readings`), а не URL. `constraints` (JSON) читається, але в цій ітерації ігнорується. Матриця кешується в памʼяті на запит; зміна в БД діє на наступний запит. Альтернатива «роль × ендпоінт × параметри з редактором» відкинута як зайва.

**Доступ до БД.** Doctrine DBAL + Migrations без ORM; репозиторії з параметризованими запитами. Сидер — окрема консольна команда (≈5 000 датчиків, повторний запуск не дублює записи за `code`).

**Список датчиків.** `LIMIT/OFFSET` із білим списком полів сортування (`name`, `code`, `created_at`) і `id` як другим ключем; `total` через `COUNT(*)` з тими ж фільтрами. Текстові фільтри — `= ?` або `LIKE 'префікс%'` із екрануванням `%`/`_`, префікс ≥3. Індекси на `name`, `code`, `created_at`. Перехід на keyset — при >10 000 рядків (ADR).

**Калькулятори.** Інтерфейс калькулятора (ім'я, режим, `calculate(sensor, window)`) і реєстр у DI-контейнері. `live` викликає `calculate`; `cached` читає `calc_results(calculator, sensor_id, window, value, computed_at)`. Реальних калькуляторів немає: контракт покривається тестовими стабами. `GET /api/sensors/{id}/readings` повертає 503, поки таблицю показань не створено консумерами. Назву таблиці й колонки (`sensor_id, ts, value`, `UNIQUE(sensor_id, ts)`) беремо з журналу рішень.

**Тести.** PHPUnit: юніт (RBAC, валідація параметрів списку, реєстр), інтеграційні з тестовою MySQL (репозиторії, міграції, індекси за ADR). Behat: логін, refresh-ротація, 401/403, список. Усе запускається в Docker.

## Risks / Trade-offs

- [XSS краде refresh із localStorage на фронті] → backend дає ротацію й відкликання refresh та короткий access; CSP і заборона небезпечного HTML — у `add-admin-frontend`.
- [Password grant застарів в OAuth 2.1, SPA бачить пароль] → прийнято для одного власного клієнта; міграція на Code + PKCE з появою сторонніх.
- [Захоплення суперадміна до першого входу] → перший вхід одразу після розгортання, не публікувати `SUPERADMIN_EMAIL`.
- [Після блокування access діє до 5 хв] → прийнято; відкликається refresh.
- [OFFSET гальмує на глибоких сторінках] → прийнято до 10 000 датчиків (ADR).
- [Контракт `readings` і `calc_results` вгадується без консумерів] → контракт мінімальний, узгодити з консумерами перед реалізацією воркера.
- [Doctrine DBAL як залежність без ORM] → використовується лише DBAL і Migrations.

## Migration Plan

1. `docker compose up`, виконати міграції, запустити сидер датчиків.
2. Задати `SUPERADMIN_EMAIL` і RSA-ключі в `.env`, одразу виконати перший вхід.
3. Відкат: міграції `down`; нових даних, що не відновлюються сидером, немає.

## Open Questions

- Екран керування користувачами в цю ітерацію не входить, тож `manager`/`user` створює консольна команда.
- Права ролі `user` не визначені; у матриці вона не має доступу.
