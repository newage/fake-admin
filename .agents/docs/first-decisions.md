# Журнал рішень: fake-admin, ітерація 1 (логін + список датчиків)

Вхідне ТЗ: [first.md](first.md). Макети стилю: [admin-styles/](admin-styles/).

## Проблема
Є сирі дані тисяч датчиків у MySQL (поки фейкові; згодом їх писатимуть окремі швидкі консʼюмери). Потрібна адмінка, яка показує ці дані та розрахунки над ними, з доступом за ролями. Без неї дані лишаються в БД без перегляду й без розмежування доступу. `fake` у назві — робоча назва, бо дані поки фейкові.

- Авторизація: JWT (access + refresh) + RBAC (яка роль які API викликає і з якими параметрами) — `first.md` і відповідь розробника.

## Концепт рішення
**Обрано (ревізія після нових вимог розробника):** підключувані калькулятори з трьома шляхами віддачі даних: (1) сирі дані — окремий ендпоінт `GET /api/sensors/{id}/readings`; (2) `live` — калькулятор рахує на запит; (3) `cached` — воркер пише результат у таблицю `calc_results`, API читає її. Режим (`live`/`cached`) оголошує сам калькулятор при реєстрації; клієнт про кеш не знає.
**Чий:** розробник (три шляхи й підключувані калькулятори), вибір «хто обирає режим» — з варіантів воронки.
**Чому:** потрібні й сирі дані, і розрахунок у реальному часі, і готові значення; контракт API стабільний, режим змінюється без зміни фронта.
**Відкинуто:**
- Початковий концепт «тільки на запит» — замінено новою вимогою розробника.
- Режим у параметрі запиту (`?mode=live|cached`) — кожен калькулятор мав би підтримувати обидва шляхи, а фронт знав би про внутрішній кеш.
- Лише попередні агрегати — не покриває сирі дані й розрахунок у реальному часі.

## Вектор
```
Browser (React SPA) ──► nginx ──► /      → статика SPA
                              └─► /api/* → PHP (Mezzio)
                                    ├─ AuthMiddleware: перевірка JWT access
                                    ├─ RbacMiddleware: роль × маршрут × параметри
                                    └─ Handler → Repository → MySQL
POST /api/auth/login   → access + refresh
POST /api/auth/refresh → новий access
GET  /api/sensors      → список датчиків (admin, manager)
nginx ──► логи → fluent-bit
Консʼюмери ──► MySQL (поза цією зміною)
```
- Фронт і API під одним origin через nginx.
- RBAC у middleware за таблицею «роль → маршрут → дозволені параметри», не в обробниках.
- Калькулятори підключаються через реєстр з режимом `live`/`cached`; сирі дані віддає окремий ендпоінт `GET /api/sensors/{id}/readings`.
- Кеш-таблицю `calc_results` заповнює воркер; у межах ітерації 1 реалізується лише контракт калькулятора (див. припущення).
- Консʼюмери й схема показань поза межами зміни; схема `sensors` лишає їм місце.

## Деталі
### Де зберігається refresh-токен на фронті
**Рішення:** localStorage.
**Чому:** вибір розробника.
**Альтернатива:** httpOnly cookie — відкинуто розробником; ціна обраного — XSS може вкрасти refresh, тому на фронті потрібна дисципліна щодо XSS (CSP, без `dangerouslySetInnerHTML`).

### Модель датчика
**Рішення:** одна величина на датчик; запис показання `(sensor_id, ts, value)`, групування фізичного пристрою пізніше полем `device_id`.
**Чому:** простіший список і найпростіший запис для консʼюмерів.
**Альтернатива:** датчик з каналами (`sensors` + `sensor_channels`) — відкинуто: JOIN у кожному запиті й складніший запис.

### Відкликання refresh-токена
**Рішення:** хеш refresh зберігається в БД (`refresh_tokens`), кожне оновлення видає новий токен (ротація); logout і блокування користувача діють одразу.
**Чому:** refresh у localStorage вразливий до XSS, тож крадіжку треба вміти відкликати.
**Альтернатива:** stateless JWT — відкинуто: відкликати не можна до закінчення терміну.

### Фільтрація й сортування списку датчиків
**Рішення:** на сервері: пагінація, сортування й фільтри — параметри `GET /api/sensors`, стан таблиці в URL (TanStack Router).
**Чому:** датчиків тисячі, а RBAC за параметрами природно лягає на серверні параметри.
**Альтернатива:** фільтрація на клієнті — відкинуто: повільний старт і не масштабується.
ADR [/docs/adr/0001-server-side-offset-pagination-for-sensors-list.md]

### Доставка схеми БД і фейкових даних
**Рішення:** Doctrine Migrations; фейкові дані (≈5 000 датчиків) заводяться окремою командою/міграцією-сидером; користувачі в сидер не входять (суперадмін — з env, решту створює адмін).
**Чому:** вибір розробника (рекомендовано було Phinx).
**Альтернатива:** Phinx — відкинуто розробником; голі SQL — без версій і відкату. Ціна обраного: залежність від Doctrine DBAL (ORM не обовʼязковий, використовувати без нього).

### Відкликання access-токена
**Рішення:** короткий access (≤5 хв) без реєстру; адмін відкликає refresh-сесії (таблиця `refresh_tokens`), access діє до закінчення терміну.
**Чому:** вибір розробника; перевірка в БД на кожен API-запит не потрібна.
**Альтернатива:** реєстр усіх токенів з `jti` (миттєве відкликання будь-якого JWT) — відкинуто розробником; ціна обраного: після блокування користувача його access діє ще до 5 хв, а «відкликати будь-який JWT» стосується лише refresh.

### Керування доступом ролей
**Рішення:** права живуть у БД (роль × ендпоінт), адмін редагує матрицю в адмінці; поле `constraints` (JSON, поки порожнє) зарезервоване під обмеження параметрів.
**Чому:** розробник вимагає керувати доступом з адмінки; єдиний ендпоінт із параметрами в ітерації 1 — список датчиків.
**Альтернатива:** роль × ендпоінт × параметри з редактором правил — відкинуто на зараз: зайва складність без реального випадку.

### Бібліотеки бекенду
**Рішення:** `monolog/monolog` (логи, збираються fluent-bit), `vlucas/phpdotenv` (env). Авторизація — OAuth 2.0 через `league/oauth2-server` (у Mezzio — `mezzio/mezzio-authentication-oauth2`); `lcobucci/jwt` лишається як її залежність. Access — JWT, підпис RS256 (пара ключів у `.env`). Refresh видає й валідує `league`; репозиторії `league` реалізуються над нашими таблицями `access_tokens` / `refresh_tokens` (у БД хеш/ідентифікатор для відкликання).
**Чому:** розробник вказав OAuth; готова реалізація стандарту надійніша за ручну.
**Альтернатива:** ручний JWT на `lcobucci/jwt` (HS256, refresh як `random_bytes`) і `firebase/php-jwt` — відкинуто на користь OAuth.

### OAuth-потік (grant)
**Рішення:** Password grant: SPA шле email + пароль на `/token`, отримує access + refresh; refresh-grant для оновлення.
**Чому:** адмінка власна й одна, сторонніх клієнтів немає, форма логіну живе у фронті.
**Альтернатива:** Authorization Code + PKCE — відкинуто на зараз: потрібна серверна сторінка логіну й consent. Ціна обраного: password grant застарів в OAuth 2.1 і SPA бачить пароль; перейти на Code + PKCE можна, коли зʼявляться сторонні клієнти.
**Звʼязок із відкликанням access:** `league` викликає `isAccessTokenRevoked` на кожен запит; за рішенням «короткий access без реєстру» метод повертає `false`, а відкликання refresh іде через `RefreshTokenRepository`.

### Як зʼявляються користувачі
**Рішення:** користувачів `user` і `manager` створює адмін в адмінці. Суперадмін (роль `admin`) заводиться з email у `.env` (`SUPERADMIN_EMAIL`): запис створюється при розгортанні з порожнім `password_hash`, а пароль встановлюється при першому вході в адмінку, після чого вхід у цей режим закривається.
**Чому:** вибір розробника.
**Альтернатива:** суперадмін із сидера з готовим паролем — відкинуто розробником; email + одноразовий `SUPERADMIN_SETUP_TOKEN` з env — відкинуто розробником.
**Ціна обраного:** до першого входу хто знає `SUPERADMIN_EMAIL` може встановити пароль першим і захопити найважливіший акаунт; мітигація — зробити перший вхід одразу після розгортання й не публікувати адресу.

### Автентифікація даних від датчика
**Рішення:** HMAC-SHA256 зі своїм секретом на кожен датчик (32 випадкові байти). Повідомлення містить `sensor_id`, `ts`, `seq`, дані та `sig`; сам секрет і його хеш у повідомлення не потрапляють. Підписується канонічний рядок з фіксованим порядком полів (напр. `sensor_id|ts|seq|value`), а не серіалізований JSON. Захист від повтору: `ts` у вікні ±5 хв, повтор усередині вікна відсікається дедуплікацією (див. нижче). `seq` лише для діагностики пропусків, не для відхилення. Канал тільки TLS.
**Видача ключа:** адмін створює датчик в адмінці, сервер генерує секрет і показує його один раз для прошивки; у БД секрет зберігається зашифрованим (libsodium secretbox, майстер-ключ з `.env`), для ротації — поле версії ключа.
**Чому:** дешево для датчика й консʼюмерів, повторюється й підміна даних ламають підпис.
**Альтернатива:** Ed25519 (на сервері лише публічний ключ, витік БД не дозволяє підробку) — відкинуто на старті, лишається шляхом оновлення, якщо апаратура дозволить; ключ у JSON — відкинуто: перехоплене повідомлення дає необмежену підробку.
**Ціна обраного:** витік БД разом із майстер-ключем дозволяє підробляти датчики; консʼюмери, які перевіряють підпис, мають доступ до розшифрованих секретів.

### Захист від дублів даних датчика
**Рішення:** дубль визначається за `UNIQUE(sensor_id, ts)` у таблиці показань. Дубль отримує успішну відповідь без запису (датчик перестає повторювати) і лічильник/лог для діагностики; при збігу `ts` з іншим `value` зберігається перше значення й пишеться попередження. `seq` використовується лише для виявлення пропусків.
**Чому:** ключ — момент вимірювання, тому дубль із будь-яким `seq` не проходить, а перезавантаження датчика (обнулення `seq`) нічого не ламає.
**Альтернатива:** `UNIQUE(sensor_id, seq)` — відкинуто: не ловить дубль із новим `seq` і блокує нові дані після перезавантаження; обидва ключі — відкинуто: два унікальні індекси на таблиці, що росте на ≈43 млн рядків/добу.
**Ціна обраного:** потрібен достовірний годинник датчика (RTC/NTP); якщо його немає, повертатись до варіанта з обома ключами. Таблицю показань створюють консʼюмери, тож унікальний індекс — вимога до їхньої схеми.

## Відкриті питання
- Годинник датчиків (RTC/NTP) — від нього залежить дедуплікація за `ts`.
- Апаратура датчиків (ESP32 чи слабший) — не блокує HMAC, визначає, чи можливий перехід на Ed25519.
- Мова й спосіб розгортання консʼюмерів, які перевіряють підпис, — поза ітерацією 1; потрібна специфікація формату підпису.
- Права ролі `user` — не визначені розробником; не блокує ітерацію 1, якщо доступ до `GET /api/sensors` мають лише admin і manager.
- Екран керування користувачами в адмінці — входить в ітерацію 1 чи наступну (див. «Припущення»).

## Припущення
- Початкова схема (не питалась, лише перегляд): `users(id, email, password_hash, role, is_active, created_at)`; `refresh_tokens(id, user_id, token_hash, expires_at, revoked_at, created_at)`; `sensors(id, code unique, name, type, unit, device_id null, location, status, secret_enc, key_version, created_at, last_seen_at)`. Таблицю показань `sensor_readings(sensor_id, ts, value, seq)` з `UNIQUE(sensor_id, ts)` консʼюмери створять окремо; в ітерації 1 вона не потрібна.
- Додаткові таблиці під нові рішення: `roles(id, name)`, `role_permissions(role_id, permission, constraints json null)`, `calc_results(calculator, sensor_id, window, value, computed_at)`.
- Обсяг ітерації 1 лишається «логін + список датчиків + контракт калькулятора»; екрани керування refresh-сесіями й матрицею прав ролей — наступна ітерація (потребує підтвердження розробника).
- Пароль зберігається як хеш (`password_hash`, bcrypt/argon2).
- Сирі показання датчиків в ітерації 1 не читаються, тож продуктивність розрахунків на запит у цій ітерації не перевіряється.
