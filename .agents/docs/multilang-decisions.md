# Журнал рішень: i18n у фронтенд-адмінці (uk + pl)

Вихідне ТЗ: `.agents/docs/multilang.md`.

## Проблема
Адмінка має інтерфейс лише українською, і мову не можна змінити. Польськомовний користувач не може нею користуватися. Потрібні вибір мови користувачем, запамʼятовування вибору та автоматичне визначення мови, коли вибору ще немає. У майбутньому мов буде більше.

## Дано
- Усі рядки UI захардкоджені українською — перевірено: `frontend/src/components/app-layout.tsx`, `features/auth/login-page.tsx`, `features/sensors/sensors-page.tsx`.
- i18n-бібліотеки немає — перевірено: `frontend/package.json`. `<html lang="uk">` зафіксований — `frontend/index.html`.
- Дати форматуються `Intl.DateTimeFormat('uk-UA')` — `sensors-page.tsx:29`.
- Zod-схема логіна містить українські повідомлення, помилки логіна мапляться на рядки — `login-page.tsx:13-26`.
- SPA роздає nginx статикою, JS не бачить `Accept-Language`, лише `navigator.languages` — `docker/nginx/default.conf`.
- Бекенд не знає про локаль, API повертає коди помилок — `docs/api.md`.
- CSP жорстка (`default-src 'self'`) — `docker/nginx/default.conf`.
- Refresh-токен зберігається в localStorage — `frontend/src/lib/session.ts`.

## Концепт рішення
**Обрано:** клієнтське визначення мови (SPA сам: збережений вибір → `navigator.languages` → `uk`).
**Чий:** запропонував розробник
**Чому:** бекенд мову не читає, тож серверне визначення додало б інфраструктуру без користі. `navigator.languages` будується з того самого `Accept-Language`.
**Відкинуто:**
- nginx читає `Accept-Language` і ставить cookie — дубль логіки в nginx і клієнті, dev-сервер Vite працює інакше, cookie стає обовʼязковою.

## Вектор
```
старт SPA ─► збережений вибір? ─так─► lang
                 │ ні
                 ▼
          navigator.languages ─► перший збіг із підтримуваними (за основною частиною: pl-PL → pl)
                 │ немає збігу
                 ▼
               uk (fallback)
lang ─► i18n-провайдер ─► тексти + Intl-локаль (дати/числа) + <html lang>
перемикач (header, справа) ─► зберегти вибір ─► lang
```
- Межа зміни: лише `frontend/`. Бекенд і nginx не чіпаємо.
- Реєстр мов один. Додати мову означає додати файл перекладу і запис у реєстр.
- Коди помилок API лишаються як є, переклад на фронті.

## Деталі
### Де зберігати вибір
**Рішення:** localStorage.
**Чому:** читає тільки фронтенд, узгоджено зі схемою зберігання токена. Відступ від ТЗ («куки») свідомий.
**Альтернатива:** cookie — їде в кожному запиті без потреби.

### Чим реалізувати переклади
**Рішення:** `i18next` + `react-i18next`.
**Чому:** множини (у польській три форми) і підстановки готові, мов буде більше.
**Альтернатива:** власний шар на `Intl.PluralRules` — свій код і свої баги.

### Мова чи локаль
**Рішення:** зберігаємо код мови (`uk`, `pl`), реєстр мов мапить його на Intl-локаль (`uk-UA`, `pl-PL`) для дат і чисел.
**Чому:** збіг із `Accept-Language` за основною частиною мови стійкіший за збіг повної локалі.
**Альтернатива:** зберігати повну локаль — крихкий збіг, більше записів.

### Перемикач
**Рішення:** у шапці зверху справа, видимий на всіх сторінках, включно з логіном.
**Чому:** вимога розробника.

## Відкриті питання
- Англійська як мова інтерфейсу — не зараз. Реєстр дозволяє додати без зміни архітектури.

## Припущення
- Fallback-мова — `uk` (поточна мова проєкту) — не блокує.
- Переклади вбудовані в бандл, ліниве завантаження — коли мов стане багато — не блокує.
- Zod-повідомлення і помилки логіна перекладаються на рендері (ключі замість рядків) — не блокує.
- Тести ініціалізують i18n з `uk`, наявні перевірки рядків лишаються валідними — не блокує.
- `<html lang>` оновлюється при зміні мови.
